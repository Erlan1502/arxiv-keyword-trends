# Data layer: ETL + SQLite

Ветка `feature/data-pipeline`. Отвечает за загрузку дампа arXiv в реляционную БД.

## Как воспроизвести (≈25 минут)

```bash
# 1. окружение
python -m venv .venv
.venv/Scripts/activate          # Windows
pip install -r requirements.txt

# 2. данные (1.88 GB, распаковывается в 5.3 GB)
curl -L -o data/raw/arxiv.zip \
  https://www.kaggle.com/api/v1/datasets/download/Cornell-University/arxiv
python -c "import zipfile;zipfile.ZipFile('data/raw/arxiv.zip').extract('arxiv-metadata-oai-snapshot.json','data/raw')"

# 3. ETL: JSON -> партиционированный Parquet
python -m src.etl.parser            # ~6.5 мин
python -m src.etl.parser --max-chunks 1   # быстрая проверка на 100k строк

# 4. Parquet -> SQLite
python -m src.db.database           # ~15 мин
```

Готовый `data/arxiv.db` **не коммитится** (`.gitignore`: `*.db`) — его собирает каждый
разработчик локально. Для проверки без полной загрузки можно ограничиться первым чанком.

## Замеры (реальный прогон, 2026-11-09)

| Метрика | Значение |
|---|---|
| строк в исходном дампе | 3 233 620 |
| прошло очистку и попало в Parquet | 3 232 618 |
| память одного чанка: до / после оптимизации типов | 132 → 98 МБ |
| память на весь файл: до / после | 4.91 → 3.83 ГБ (**−22 %**) |
| время ETL | 374 с |
| объём Parquet | 2.2 ГБ, 36 партиций `year=1991 … year=2026` |
| время загрузки в SQLite | см. вывод `python -m src.db.database` |

Требование силлабуса «>200 МБ / >500k строк» перевыполнено на порядок.

## Три решения, которые стоит объяснять на защите

**1. Год берётся из `versions[0].created`, а не из `update_date`.**
`update_date` — дата последнего изменения. По ней статья 1995 года, отредактированная
в 2020-м, попадает в 2020-й и портит динамику. В дампе таких записей сотни тысяч.

**2. Колонка `year` не пишется внутрь Parquet.**
Каталог называется `year=2026` — это Hive-партиция, pyarrow восстанавливает колонку
из имени каталога. Если записать её ещё и в файл, при чтении возникает конфликт
`int16 vs dictionary<...>`.

**3. Индексы и внешние ключи включаются ПОСЛЕ загрузки.**
Поддержка 6 индексов и проверка FK на каждой из ~19 млн вставок замедляют загрузку
в разы. После загрузки выполняется `PRAGMA foreign_key_check`.

## Аналитические запросы

8 запросов в [`queries.sql`](queries.sql), каждый помечен требуемой конструкцией:

| # | Конструкция | Что считает |
|---|---|---|
| Q1 | JOIN | топ-20 категорий по числу статей |
| Q2 | GROUP BY + HAVING | крупные категории среди статей с 2015 |
| Q3 | подзапрос | статьи с аннотацией длиннее средней |
| Q4 | CTE | динамика 10 самых частых ключевых слов по годам |
| Q5 | RANK | топ-5 категорий в каждом году |
| Q6 | LAG | годовой прирост числа статей, % |
| Q7 | CTE + RANK | топ-5 ключевых слов в каждом году |
| Q8 | JOIN + агрегация | самые продуктивные авторы |

```bash
sqlite3 data/arxiv.db < src/db/queries.sql
```

## Известные ограничения

1. **`paper_keywords` пуста.** Таблица заполняется модулем NLP (`src/nlp/`, ветка
   `feature/nlp-keyword-extraction`). До мержа Q4/Q7 возвращают 0 строк — это
   ожидаемо, а не ошибка схемы.
2. **Авторы не различаются по id.** В исходном дампе есть только имя, поэтому
   Q8 склеивает однофамильцев: `Liu Yang` с 3 179 статьями — это, скорее всего,
   несколько разных людей. Для честного рейтинга нужна дедупликация по
   `arxiv_id` + аффилиации, которой в датасете нет.
3. **1991 год неполный** — arXiv стартовал в августе 1991, поэтому 353 статьи
   этого года дают взрывной «рост» в Q6 (+799.7 %). При интерпретации динамики
   первые два года следует отбрасывать.
